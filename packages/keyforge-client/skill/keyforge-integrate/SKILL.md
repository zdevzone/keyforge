# Integrate KeyForge into a dependent app

Inspect the target application's language, runtime, onboarding, protected operations, storage and test workflow first. Use `@keyforge/client` where its Fetch/Web Crypto runtime requirements fit; do not assume Electron, invent a backend, or add a second auth system. Ask for the deployment URL, stable product ID and trusted public keys when unavailable. Product/license keys are customer inputs; the SDK automatically creates the separate installation secret.

Read [the integration contract](references/integration.md) before changing licensing. Prefer the installed SDK README/types and this contract; when the KeyForge source repository is available, consult `docs/dependent-app-integration.md`, `docs/verify-token.md`, `docs/client-openapi.json` and `examples/keyforge-node.ts`. Do not infer API fields from old unscoped routes or JWT libraries.

## Implement the host integration

- Add the publishable SDK archive/workspace dependency using the target repository's package manager. The package may not yet be on a public registry; obtain the built archive/source rather than installing an unrelated similarly named package. Respect target framework/version and existing UI components.
- Implement and test a platform-appropriate `SecureStorage` adapter. Keep one SDK owner in a trusted process, expose only required status/actions to UI, and atomically persist a coherent state record. Use the existing credential vault or a vault-held encryption key plus atomic encrypted-file replacement. Never silently fall back to plaintext persistence or `MemoryStorage` in production.
- Offer online key activation and provider-permitted trial onboarding. Skipping leaves the app unlicensed with only explicitly free app features. Enforce access at actual protected operations, including backend/IPC boundaries where present, rather than only hiding buttons.
- Refresh while online ahead of the signed deadline; evaluate cached authorization on startup and at protected operations. Handle expired/revoked/reconnect states visibly. Keep app-specific trial usage durable and separate from token refresh. Preserve the target app's work/data when authorization ends.
- For optional Windows recognition, import `createWindowsDeviceSignalsProvider` from `@keyforge/client/windows` in the trusted Node process and supply `deviceSignalsProvider`. Keep Node imports out of browser/mobile bundles. Do not collect CPU IDs, MAC/IP addresses or send raw identifiers. Read the SDK's Windows diagnostics and recovery guidance; partial/unsupported reports must leave installation-based licensing usable. Backfill existing installations with `updateDeviceSignals()`, never a new registration request. Preserve secure storage and the original registration body across restarts. Explain URL/product scoping, legacy backfill and recognition limitations; do not describe this as physical-device enforcement.
- For Windows/Linux/macOS targets, prefer the automatic `createDeviceSignalsProvider()` from `@keyforge/client/device-signals`; explicit `/linux` and `/macos` factories also exist. Never request sudo to read Linux DMI identifiers. Honor missing/permission-denied signals and OS-specific complete sets (Mac two; Windows/Linux three). Browser/mobile sandbox limitations remain. For non-JS/TS apps, use the HTTP/OpenAPI and exact hash/token contracts; do not claim a native SDK exists or introduce Node just to wrap REST. Consult `docs/device-identity.md` when available and the packaged README; choose language-specific ports only for a real target's needs.
- For optional inbox/notifications, use public customer methods and polling/backoff. Add a durable app outbox for support messages; keep UUID/body unchanged after timeouts. Do not imply that email delivery or customer portal accounts exist.

Avoid handling signing secrets, admin tokens, financial operations or trusted metering credentials in the client. Never print keys, tokens, installation state, request-link secrets or authorization headers in tools/logs. Reading public key material is sufficient for verification. Installing this skill does not authorize modifying live operator/license data.

## Verify the integration

Test against an isolated KeyForge fixture or provider-approved test product. Verify online activation, offline restart within grace, reconnect after grace, altered/wrong-context tokens, signed HTTP-200 revocation, interrupted registration, exhausted seats, disabled/spent trials and retained consumption. Test the host storage adapter for atomic-save failure/restart and single-owner serialization. For communication, verify exact message replay and isolation from other installations/internal notes. Run the target repository's checks and explain runtime/storage limitations. Do not reset the server or issue live licenses merely to exercise the integration.
